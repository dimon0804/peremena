# Нагрузка и масштабирование

Цель — выдержать масштаб «все школы региона»: тысячи школ, сотни тысяч родителей, пики утром,
с 20:00 до 22:00 и при сборе на всю параллель, — и расти добавлением экземпляров.

Ниже — что было узким местом, что сделано и замеры до и после. Скрипты и сырые результаты — в
[`loadtest/`](../loadtest/README.md) (`loadtest/results/*.json`).

## Стенд

- Ноутбук: Intel i7-12650H (16 потоков), Windows 11, Python 3.12 без uvloop (на Linux в Docker с uvloop
  и httptools обработка быстрее — цифры ниже скорее занижены). Параллельно на машине работали другие процессы,
  разброс между прогонами — до ±20 %.
- PostgreSQL 16 и Redis 7 в Docker (`postgres:16-alpine`, `redis:7-alpine`), бот — процессы `python -m app run`
  на хосте, перед ними — генератор нагрузки, который раскладывает запросы по экземплярам по кругу, как балансировщик.
- Поддельный MAX API (`loadtest/fake_max.py`) отвечает за 10 мс, считает каждый вызов и в сценарии (а) пропускает
  не больше 30 запросов в секунду — сверх отвечает 429, как настоящий MAX.
- «До» — исходный коммит `7488be7`. Единственная правка для замера: лимит запросов к MAX читается из окружения,
  чтобы в сценарии (б) мерить само приложение, а не лимит MAX.

## Сценарии

| | Что происходит | Объём |
|---|---|---|
| (а) | завуч запускает сбор на параллель через API, затем родители жмут кнопку | 10 классов × 30 родителей: 310 сообщений, 300 нажатий за 5–10 с (+5 % повторных доставок) |
| (б) | пик вебхуков: сообщения в чатах классов (10 % — вопросы) и нажатия кнопок сбора, 3 % повторных доставок в другой экземпляр | 1700 классов, ~51 000 пользователей; 500 / 1000 / 2000 событий в секунду по 10 с |
| (в) | мини-приложение: «Мои сборы» с подписью данных запуска MAX | 200 родителей одновременно и непрерывно, 20 с |

После каждого сценария — сверка в базе и в поддельном MAX: каждому родителю ровно одно сообщение сбора,
каждый callback отвечен ровно один раз, каждый ответ и каждый вопрос записан ровно один раз.

(Redis): пик к MAX — 26 запросов в секунду при любом числе экземпляров.

До: взаимная блокировка пула. Запрос брал соединение, а внутри открывал вторую сессию (классы родителя) —

## Узкие места и что сделано

| Где | Проблема | Что сделано |
|---|---|---|
| `bot/router.py`, `updates.py` | задача на каждое событие без потолка → пул базы кончается, события теряются | `HANDLER_CONCURRENCY` — потолок одновременно обрабатываемых событий на процесс |
| `updates.py`, новый `events.py` | приём вебхука и обработка в одном процессе: на пике ответ MAX задерживается на секунды; необработанное живёт в памяти и пропадает при падении | очередь событий в Redis Streams: вебхук делает XADD и сразу 200, обрабатывают все `all`/`worker` группой потребителей, XAUTOCLAIM подбирает события умершего обработчика |
| `main.py` | три `@app.middleware("http")` (BaseHTTPMiddleware) на каждом запросе | вебхук — отдельным ASGI-путём, остальные правила — один ASGI-слой `HttpPolicy` |
| `services/polls.py`, `pending_for_user`, `record_answer` | вложенная сессия — два соединения на запрос → взаимная блокировка пула | проверки тем же соединением, классы — до открытия сессии |
| `max_api.py` | лимит MAX в памяти процесса: N экземпляров = N × 25 запросов/с → 429 | общий ограничитель в Redis (Lua, часы Redis), пауза после 429 — тоже общая; без Redis — локальный |
| `updates.py`, `main.py` | планировщик в каждом процессе: N экземпляров = N рассылок напоминаний и сводок | лидер по замку (Redis `SET NX PX` с продлением, без Redis — `pg_try_advisory_lock`), `ROLE=all/web/worker` |
| `bot/router.py` | замок «события одного человека по очереди» — в памяти процесса | `kv.lock()`: в Redis общий для всех экземпляров, с продлением; без Redis — локальный |
| `services/polls.py` | «рассылается сейчас» — множество в памяти процесса | отметка в общем хранилище (`dispatching:<id>`, срок 15 мин) |
| `polls.tick`, `resume_dispatch` | каждую минуту — все открытые сборы региона со списками получателей (десятки тысяч × 30 строк) | в базе отбираются только сборы со сроком или напоминанием, без списков, пачками по курсору (срок, id) |
| `quiet.morning_tick` | каждую минуту — все учителя в память и `is_teacher` на каждого | окно «утро» считается на часовой пояс, учителя отбираются в базе пачками; поясов — единицы |
| `polls.after_answer` | на каждый ответ — загрузка всех получателей и сверка со списком класса | один `COUNT`; сверка — только когда ответили все |
| `webapp/api.py`, `shelf.chat_titles` | на каждый запрос API — названия **всех** классов базы | только нужные id; учителя для «Моих сборов» — одним запросом |
| `services/search.py` | признаки карточек справочника пересчитывались на каждый вопрос | кэш признаков по тексту карточки |
| `db.py` | пул по умолчанию, `pool_pre_ping` — лишний запрос на каждую сессию | `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`, `DB_POOL_TIMEOUT`, `DB_PRE_PING`, `pool_recycle` |
| `db.py` | несколько экземпляров стартуют вместе — миграции наперегонки | `pg_advisory_xact_lock` на время миграций |
| `models.py` | нет составных индексов под горячие запросы | миграция `scale0005`: 13 индексов (сборы, получатели, участники, входящие, доска, пропуски, статистика) |
| `board.tick` | все отложенные записи разом | пачками по 500 |

## Что остаётся потолком

- **Лимит MAX — около 30 запросов в секунду на бота** (по документации платформы; на настоящем MAX не проверялось).
  Масштабированием бота его не обойти. Рассылка 300 родителям — ~13 с; региональная рассылка на 10 000 родителей —
  ~7 минут. Ответы на нажатия кнопок тоже идут через этот лимит: на пике в 2000 событий/с с 15 % нажатий
  (300 нажатий в секунду) ответы на кнопки копятся в очереди и уходят со скоростью ~25 в секунду. Отсюда вывод для
  продукта: массовые рассылки растягивать по времени, а на пике не отвечать на кнопку отдельным сообщением,
  где без него можно обойтись. Если платформа даст боту больший лимит — достаточно поднять `MAX_RPS`.
- **Процессор на событие** — ~5 мс Python (SQLAlchemy и разбор событий). Один процесс-обработчик — 150–200 событий
  в секунду; обработка масштабируется числом воркеров почти линейно, пока не упрётся в PostgreSQL.
  На стенде три обработчика дали ~350 событий/с — дальше мешали общий ноутбук и база в WSL.
- **PostgreSQL** — одна база. Соединений: `(экземпляры × WEB_CONCURRENCY) × (DB_POOL_SIZE + DB_MAX_OVERFLOW)`;
  при десятках процессов — PgBouncer в режиме транзакций перед базой.

## Как масштабировать в проде

```bash
# одинаковые экземпляры за внутренним балансировщиком lb (хостовый nginx по-прежнему ходит на 127.0.0.1:${BOT_PORT})
docker compose up -d --scale bot=3

# прод-схема: приём отдельно, обработка отдельно
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --scale bot=3 --scale worker=4
```

- `bot` (ROLE=web) — по числу HTTP-запросов: вебхуки и мини-приложение.
- `worker` (ROLE=worker) — по длине очереди событий: метрики `peremena_queue_lag` и `peremena_queue_pending`
  на `/metrics`, `python -m app events` или `redis-cli XINFO GROUPS pm:events`.
- Лидер планировщика — всегда один; упал — через ≤30 с его место занимает другой, штатная остановка — сразу.
- Проверено на стенде Docker Compose: `--scale bot=3` — три экземпляра за `lb`, лидер ровно один, остановка
  лидера → новый лидер через 2 с; `docker-compose.scale.yml` — 2 web (по 2 процесса uvicorn) + 2 worker, лидер — один из worker.

## Один VPS 2 vCPU / 4 ГБ

Вопрос: сколько классов держит один сервер 2 vCPU / 4 ГБ, на котором стоит всё сразу — бот, PostgreSQL, Redis
и балансировщик. На слайде было «≈ 100 классов» без замера. Ниже — замер.

### Стенд

- Домашний сервер: Intel Core i5-2500 (4 ядра, 3,3 ГГц, 2011 год), 9 ГБ памяти, Ubuntu, Docker. Рядом работали
  другие сервисы (их не трогали).
- Весь стек «Перемены» — в лимитах профиля [`docker-compose.vps.yml`](../docker-compose.vps.yml):
  бот 1,4 CPU / 1280 МБ, PostgreSQL 0,4 CPU / 2 ГБ, Redis 0,1 CPU / 512 МБ, балансировщик Caddy 0,1 CPU / 256 МБ.
  В итоговой серии у балансировщика остался прежний лимит 0,15 CPU (контейнер не пересоздавался — скрипт теперь
  это делает), то есть всего было 2,05 CPU; сам балансировщик занимал в среднем 0,05 CPU, на пике 0,14.
- Бот — один контейнер, два процесса uvicorn (`WEB_CONCURRENCY=2`, `ROLE=all`): каждый принимает вебхуки и разбирает
  очередь Redis. `HANDLER_CONCURRENCY=32`, пул базы 8 + 8 на процесс, `ACCESS_LOG=false`.
- Поддельный MAX ([`loadtest/fake_max.py`](../loadtest/fake_max.py)) отвечает за 10 мс, пропускает не больше
  30 запросов в секунду, сверх — 429, как настоящий. Он и генератор нагрузки — отдельные контейнеры на той же машине,
  вне лимитов.
- Путь запроса: генератор → балансировщик → бот. TLS не моделировался: на настоящем VPS его снимает хостовый
  nginx/Caddy, и это ещё немного процессора.
- Каждая ступень: база засеяна ровно на N классов (30 родителей и учитель в классе, школы по 10 классов, в каждом
  классе открыт сбор), Redis очищен, бот перезапущен, 120 с нагрузки, затем ожидание, пока всё не обработано.
  Скрипты: [`loadtest/vps_stress.sh`](../loadtest/vps_stress.sh), [`loadtest/vps_profile.py`](../loadtest/vps_profile.py);
  результаты — `loadtest/results/vps-*.json`.

### Модель вечернего пика (расчёт, не замер)

На один класс (30 родителей и учитель), 20:00–22:00:

| Что | Интенсивность на класс | Смысл |
|---|---|---|
| Сообщения в чате класса | 0,06 в секунду | 3–4 сообщения в минуту; 10 % — вопросы, попадают в «частые вопросы» |
| Нажатия кнопок сбора | 0,02 в секунду | весь класс отвечает на сбор за 25 минут; каждый родитель жмёт один раз |
| «Мои сборы» в мини-приложении | 0,02 запроса в секунду | каждый родитель открывает 2–3 раза в час |
| Повторные доставки MAX | 3 % событий | MAX не дождался 200 и прислал снова |
| Сбор на параллель | один на ступень | завуч рассылает сбор на 5 классов (150 родителей), они отвечают за 10 с |

Для 100 классов это 8,2 вебхука в секунду, 2 запроса мини-приложения в секунду и рассылка на 150 родителей.
Модель с запасом: 0,06 сообщения в секунду два часа подряд — это 430 сообщений на класс за вечер, в живом чате
их в разы меньше. По сути это «горячие 10–15 минут» после объявления учителя, причём во всех классах сразу.
Ступени 300, 1000, 1200, 1500, 3000 — та же модель, умноженная на число классов.

длиннее `EVENT_BACKLOG_WARN`. Пропускная способность за потолком (1200–3000 классов, очередь не пустеет) —
**81–85 событий в секунду** вместе с 24–60 запросами мини-приложения в секунду.

### Где потолок

- **Упор — процессор бота.** С 1000 классов бот съедает весь свой лимит, PostgreSQL — треть ядра, Redis
  и балансировщик — единицы процентов. Память не кончается нигде: весь стек под пиком — до 0,5 ГБ из 4.
- **Очередь.** До 1000 классов она не растёт: пик 188, после нагрузки разобрана за секунды. На 1200 растёт
  примерно на 11 событий в секунду, на 1500 — 4 800 к концу нагрузки, на 3000 — 23 770 (разбор ещё 4 минуты).
- **Вебхук не деградирует даже за потолком:** p95 не выше 134 мс на всех ступенях, все ответы 200 — MAX не
  повторяет доставку, события ждут в очереди. Порог «p95 вебхука > 1 с» не достигнут ни разу (максимум отдельного
  запроса — 0,98 с на 3000 классах).
- **Что видит родитель.** На 1000 классах ответ на кнопку — p50 1 с, p95 2,2 с, «Мои сборы» — p95 около 1 с:
  это уже край. На 300 классах всё быстрее 0,2 с.

- Процессор отдан боту: при 1,2 CPU он упирался в лимит, а PostgreSQL до своих 0,5 не доходил (пик 0,42).
  После переноса 0,1 CPU от базы и 0,05 от Redis ответ на кнопку на 1000 классах стал в 2,5 раза быстрее,
  пропускная способность за потолком выросла с 76 до 85 событий/с. Полная серия со старым делением —
  `vps-real-{100,300,1000,1500,3000}.json`, промежуточная проба — `vps-tuned-{1000,1500}.json`.
- Два процесса uvicorn — лучший вариант. Один процесс Python не использует больше одного ядра — очередь растёт
  уже на 1000 классах. Три — та же пропускная способность, но медленнее ответы и на 90 МиБ больше памяти.
- Лимит MAX на этих ступенях — не главное: без него пропускная способность выше на 8 % (92 против 85 событий/с).
- Не варьировали, потому что не были узким местом: пул базы (ни одного таймаута пула), `shared_buffers`
  (PostgreSQL — до 200 МиБ), `HANDLER_CONCURRENCY`.

### Вывод: сколько классов держит

- **По замеру: один VPS 2 vCPU / 4 ГБ с профилем `docker-compose.vps.yml` держит вечерний пик ~1000 классов
  (~31 000 пользователей) без роста очереди и без потерь; с ответами быстрее 0,2 с — до 300 классов.**
- **100 классов** (как на слайде): бот в среднем 25 % одного ядра, база 5 %, весь стек — 345 МиБ памяти, ответ
  на кнопку p95 0,1 с, «Мои сборы» p95 34 мс.
- Запас для 100 классов (расчёт по замеру): по пропускной способности — около ×10 (8,6 события/с против 81–85);
  по «ответам быстрее 0,2 с» — ×3; по памяти — ×8 и больше.

Что не проверено и может сдвинуть цифры:
- процессор настоящего VPS: здесь i5-2500 2011 года; vCPU облачного сервера бывает и быстрее, и медленнее
  (часто это половина физического ядра) — если он вдвое медленнее, потолок по расчёту ~500 классов;
- TLS на хостовом nginx/Caddy и задержка настоящего MAX (здесь 10 мс);
- долгая работа: ступени по 2 минуты, рост базы за учебный год не моделировался;
- память под систему: лимиты контейнеров в сумме — ровно 4 ГБ, а ОС на VPS тоже нужно место
  (фактически стек занял 0,5 ГБ, так что запас на деле есть).

### Находки по ходу

- **Ответ на нажатие терялся при обрыве соединения.** В прогоне `vps-tuned-1500.json` (до исправления) один из 3 750
  ответов на кнопку не дошёл до MAX: `ReadError` на переиспользованном соединении, а `POST /answers` не повторялся —
  как отправка сообщения, где повтор дал бы дубль. Для ответа на нажатие повтор безопасен (тот же callback, то же
  уведомление) — теперь повторяется (`max_api.py: answer_callback`). В итоговой серии потерь нет.
- **Гонка в очереди.** Событие, подобранное `XAUTOCLAIM`, могло обработаться ещё раз, если первая копия тем временем
  ушла в dead-letter или закончилась. Нашёл тест на настоящем Redis; теперь событие, которого уже нет среди
  неподтверждённых, пропускается.
- **Сообщение сбора 149 из 150.** В одном прогоне из десяти (`vps-real-1000.json`) генератор на момент проверки
  увидел 149 сообщений сбора из 150; ошибок в логе нет, дублей нет, в остальных прогонах — 150 из 150. Вероятно,
  часть рассылки довела минутная задача планировщика уже после ответа API — не проверено. Генератор теперь ждёт
  сообщения до 60 с.
- **Память Redis под очередь.** 23 770 событий в очереди — 22 МиБ в Redis, ~0,6–0,9 КБ на событие. Поток
  хранит и обработанные события до `MAXLEN`; по умолчанию это 1 000 000 — до гигабайта, для 4 ГБ слишком много.
  В профиле VPS `EVENT_STREAM_MAXLEN=200000` (~160 МБ, расчёт).
